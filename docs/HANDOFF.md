# 인계 문서

이 프로젝트를 이어받는 사람(또는 에이전트)을 위한 문서다. 먼저 이 문서를 읽고, 규칙은 `docs/design/`, 수치 관찰은 루트 `README.md`를 본다.

## 1. 한 줄 요약

삼국지 소재의 6인 그리드 전략 RPG(전국란스 스타일)에서 **전투 엔진 + Balance Lab**을 만들어 전투 밸런스를 검증하는 단계다.
정식 게임이 아니라 "숫자를 바꿔 가며 계속 싸워보고 싶은 전투 샌드박스"가 첫 성공 기준이다.

- 완료: 순수 TypeScript 전투 엔진, 시뮬레이터, CLI, Balance Lab(React + Vite + Web Worker), 설계 문서 2건
- 다음: PixiJS 전투 화면(뷰어 → 수동 플레이) → 규칙 확장(가드, 필살기, 상태이상, 승급)
- 지금은 지역 제패, 스토리, 아트, 캐릭터 대량 제작을 하지 않는다.

## 2. 시작하기

환경: Node 22, npm 10 (워크스페이스). TypeScript 7.x, Vite 8, Vitest 5를 쓴다 (일반적인 버전보다 새 것이니 이상하면 먼저 의심한다).

```bash
npm install
npm test                 # 105개 (엔진 단위, 실제 데이터 통합, Lab 로직/렌더링/워커)
npm run typecheck        # 4개 패키지를 각각 tsc -p 로 검사
npm run lab              # Balance Lab (터미널에 나오는 주소를 연다)
npm run sim -- --iterations 10000 --lineups random     # CLI 시뮬레이션, 옵션은 README 참고
```

## 3. 구조와 의존 방향

```text
apps/balance-lab/    React + Vite. 시뮬레이션은 Web Worker에서 실행
packages/battle-engine/   순수 TypeScript. React/PixiJS/DOM에 의존하지 않는다 (tsconfig에서 DOM 타입도 막아 둠)
packages/game-data/       병종, 특성, 스킬, 캐릭터, 밸런스 수치, 기본 편성. 엔진의 "타입"만 가져온다
tools/sim/                시뮬레이션 CLI
docs/design/              기획 문서 (01 캐릭터·병종·상태이상, 02 전투 규칙)
```

- 엔진은 **데이터를 인자로만 받는다** (`GameData`, `BalanceConfig`). 그래서 Lab이 메모리에서 수치를 고쳐 게임과 같은 엔진을 돌린다.
- 규칙은 React/PixiJS에서 계산하지 않는다. 화면은 엔진의 `BattleEvent` 스트림을 재생하는 쪽으로 만든다.
- 데미지 공식은 `DamageCalculator` 한 곳, 판정은 `judgement.ts` 한 곳이다. 숫자는 코드에 넣지 않고 `game-data`의 데이터로 둔다.
- 엔진은 결정적이다. 난수는 시드 기반(`rng.ts`)만 쓰고 `Math.random`은 쓰지 않는다. 1대1처럼 속도가 다르면 결과도 매번 같다.

주요 파일: `engine.ts`(라운드 루프, 행동, 반격, 사기, 열 이동), `damage.ts`, `targeting.ts`, `policy.ts`(커맨드 선택 AI), `simulator.ts`(통계 집계, 무작위 편성), `lineup.ts`, `judgement.ts`.

## 4. 핵심 설계 결정 (자세한 내용은 설계 문서)

| 항목 | 결정 |
|---|---|
| 전투 방식 | **라운드제 + AP 총량.** 라운드마다 속도순으로 AP가 남은 군단이 1회 행동. AP는 전투 전체 예산이고 회복되지 않는다 (풍수사 AP 회복형 승급만 예외, 미구현). 행동 게이지는 폐기 |
| HP | 군단전은 **병력**. 군단 레벨당 +50 (Lv1 300, Lv15 1000) |
| 피해 | 병력이 많을수록 강하다 (`clamp(현재 병력 / 1000, 0.3, 1.75)`). 방어는 `1 / (1 + 방어 × 0.1)`, 책략은 대상의 지력으로 경감 |
| 반격 | 근접 일반공격만 반격 피해를 받는다 (× 0.5). 원거리(화살/책략/독연)는 일방적 |
| 상성 | **상성표 없음.** 병종 차이는 "특성"(조건부 피해 보정)으로 표현하는 체계가 있으나, 지금은 어떤 병종에도 붙이지 않았다 |
| 사기 | 제로섬 단일 막대, **5:5 시작, 피해에 영향 없음, 최종 판정에서만 사용**. 판정에서의 구체적 쓰임은 해석이 들어 있다 (아래 미정) |
| 판정 | 전멸 군단 수 → 잔여 병력 → 사기 → 방어측 |
| 종료 | 한쪽 전멸 / 모두 AP 소진 / 교착(한 라운드 동안 대기 외 행동 없음) / `maxTurns` 40 |
| 열 | 전열 3 + 후열 3. 전열이 전멸하면 후열이 즉시 전열이 된다 |
| 병종 | 6계열(보병, 기병, 궁병, 책사, 도사, 풍수사) × 승급 2갈래. 승급 병종은 미구현. 병종은 캐릭터당 고정 |
| 커맨드 | 일반공격 + 특수행동 + 필살기(유니크) + 대기. 일반공격은 병종이 정의하고 승급하면 2로 교체 |
| 대상 선택 AI | 기본 "예상 피해가 큰 적". 시뮬레이션 전용 가정이며 결과를 크게 좌우한다 |

문서의 확정도 표기: **[확정]**(사용자가 직접 결정) · **[기본값]**(제안했고 이의 없이 채택) · **[임시]**(수치 가설) · **[미정]**. 이 표기를 유지한다.

## 5. 구현 현황

| 구현됨 | 아직 없음 |
|---|---|
| 일반공격, 치유, 대기, 반격, 병력 비례 피해, 병종 특성 체계, 제로섬 사기, 전열 전멸 시 후열 이동, 승패 판정, 교착 종료, 진영당 1~6군단 가변 편성, 무작위 편성 모드, 병종별 병력 배율(`troopScale`), 치유 병력 보정 옵션 | 가드(방패병), 필살기, 상태이상(화상/독/젖음), 책략의 날씨·지형 변환, 승급 병종, AP 회복, 아이템, 군단 경험치, 일기토/개별 레벨/토벌, 특수 병종, **PixiJS 화면, 수동 플레이** |

책략/독연은 지금 피해만 준다. 캐릭터 12명과 수치는 전부 임시값이고 이름만 삼국지다 (`packages/game-data/src/data.ts`).

## 6. Balance Lab 주의점

- **Lab에서 고친 값은 `game-data` 코드에 자동 반영되지 않는다.** 브라우저 localStorage에만 저장된다 (키 `samgukji-balance-lab-v2`). 채택할 값은 "밸런스만 내보내기"(CLI `--balance`로 검증 가능)나 "전체 상태 내보내기"로 꺼내 코드에 옮긴다.
- 기본 수치를 바꾸면 저장 키 버전을 올린다 (옛 저장값이 새 기본값을 가리는 문제를 이미 한 번 겪었다). 새 필드를 추가하면 `LabContext.tsx`의 `normalizeState`에서 기본값을 채운다.
- 화면을 **브라우저로 직접 확인하지 못했다.** 타입 체크, 빌드, 개발 서버 응답, 서버 렌더링 스모크 테스트, 워커 프로토콜 테스트로만 검증했다. 먼저 한 번 열어서 레이아웃과 동작을 확인한다.
- 병종/캐릭터별 승률은 **무작위 편성** 모드에서만 의미가 있다 (고정 편성은 편성 편향이 섞인다).

## 7. 시뮬레이션에서 알게 된 것 (함정)

- **AI 정책이 결과를 크게 좌우한다.** 같은 데이터에서 타겟 AI만 바꿔도 병종 승률과 생존율이 크게 변한다. 밸런스 수치를 맞추기 전에 AI 가정을 먼저 정한다.
- 집중 공격 AI("현재 병력이 가장 적은 적")는 `troopScale`이 다른 병종을 항상 먼저 노린다 (병력 배율 1.0 → 0.99에서 풍수사 생존율 89% → 22%). 병력 비율 기준으로 고치는 안이 있다.
- 전투의 98%가 전멸이 아니라 AP 소진 후 판정으로 끝난다. 1대1에서는 AP 4로 서로 못 죽이고, 속도 1 차이가 승패를 가른다 (병력 보정 눈덩이).
- 사기를 피해 보정(±10%, 시작 60:40)으로 쓰면 5라운드 안팎의 짧은 전투에서 증폭되어 방어측이 73% 이겼다. 그래서 피해 영향을 껐다.
- 현재 기본 수치의 신호: 풍수사 승률 59%(치유 과다), 보병 37%(약함), 기병 56%(강함), 궁병 생존율 65%(목표 20%). 수치는 임시이고 조정 대상이다.
- 통계의 `damageTaken`은 병력에서 막히므로 "더 센 공격"의 지표로 못 쓴다. 생존율이나 라운드 수를 본다.

## 8. 확장 계획이 코드에 주는 영향

사용자는 나중에 **9대9**와 **공성 상황**으로 넓힐 계획이다. 지금은 6대6 기준으로 만들었고, 아래가 고정돼 있다.

| 위치 | 현재 | 확장 시 |
|---|---|---|
| `lineup.ts` | `MAX_UNITS_PER_SIDE = 6`, `ROW_CAPACITY = 3`, `generateRandomLineup`의 기본 크기 6 | 9로 올리고 열 구조를 정한다 |
| `types.ts` `Row` | `'front' \| 'back'` 2열 | 9대9가 3열(전/중/후)이면 `Row`, `TargetRule`, 특성의 `versus.rows`, `advanceRows`(전열 전멸 시 이동), 설계 문서의 "전열/후열"이 모두 바뀐다 |
| Lab `slots.ts` | `SLOT_COUNT = 6`, `FRONT_SLOTS = 3`, `LabContext`의 `teamA.length === 6` 검증, `LineupEditor` | 슬롯 수와 열 표시를 일반화한다 |
| 판정/사기 | 군단 수 가변은 이미 지원 | 그대로 쓸 수 있다 |
| 공성 | 없음 | `BattleContext`(날씨·지형)를 아직 만들지 않았다. 성벽/성문 같은 전장 요소는 새 규칙이므로 `docs/design/`에 먼저 정의한다 |

엔진은 "진영당 군단 수"를 이미 가변으로 다루므로(1~6), 수를 늘리는 것 자체는 쉽다. 어려운 것은 **열이 2개를 넘을 때의 규칙**이다.

## 9. 다음 작업 제안

1. **PixiJS 뷰어 MVP** (`apps/game` 새 앱 권장): 12슬롯 필드, 이름·병력 바·AP, 공격/반격/치유 연출, 데미지 숫자, 전멸·열 이동, 재생 속도. 임시 도형으로 시작한다. 엔진의 `BattleEvent`가 계약이다 (필요하면 위치/열 정보를 이벤트에 더한다).
2. **수동 플레이:** 한쪽을 플레이어가 조작한다. 엔진의 `run()`은 정책이 끝까지 돌리는 구조라서, "한 행동씩 진행하고 커맨드를 받는" API(`step()` 등)가 필요하다. 재미 판단은 이 단계부터 가능하다.
3. **규칙 확장:** 가드, 필살기, 상태이상, 승급을 확정되는 순서대로 추가한다. 항목마다 엔진 이벤트와 화면 표현, Lab 수치를 같이 넣는다.

미정 결정 사항은 `docs/design/01-...md` 8장, `02-...md` 8장의 표에 모여 있다. 특히 급한 것:

- 사기를 최종 판정에 쓰는 방식 (지금은 3번째 동률 기준이라 사실상 영향이 없다. `balance.morale.judgement`로 순서를 바꿔 볼 수 있다)
- 필살기 배율, 2단계 군단 일반공격에 반격을 적용할지
- 가드의 광역/책략 처리 외 세부, 도사 승급 방향
- 병종 간 균형을 어떤 AI 가정으로 볼지

## 10. 작업 방식 (사용자 선호와 합의)

- 사용자는 한국어로 소통하고, 웹 프론트엔드(React) 경험이 있다. 게임 엔진(Unity)은 쓰지 않기로 했다.
- **기획을 확정하고 문서화한 뒤 구현한다.** 해석이 들어간 부분은 "제 해석"이라고 밝히고 문서에 [기본값]/[미정]으로 남긴다.
- 숫자는 데이터로 분리하고, 전투 로직과 렌더링을 분리한다. 임시 UI와 임시 아트를 쓴다. 아트를 먼저 만들지 않는다.
- **원작(전국란스) 게임 파일을 추출·디컴파일하지 않기로 했다** (EULA/저작권, Steam 출시 목표, 원작 수치가 우리 규칙과 맞지 않음). 원작은 사용자의 설명과 직접 플레이한 관찰로만 참고한다. 원작 세부 규칙에 대한 설명은 기억 기반이라 틀릴 수 있다.
- 실험할 때는 `tools/sim/src/_이름.ts` 임시 스크립트를 만들어 `npx tsx`로 돌리고 **삭제한다.** 저장소에 남기지 않는다. 오래 쓸 도구는 CLI 옵션이나 Lab 기능으로 승격한다.
- 원본 기획서(`samgukji_strategy_rpg_agent_spec.md` v0.1)는 대화로 전달되었고 **이 저장소에 포함되어 있지 않다.** `docs/design/01`이 상위 문서로 참조한다. 원본을 `docs/spec/`에 추가하길 권한다.
