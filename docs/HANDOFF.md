**지금까지 만든 것**

- **Balance Lab**: 시뮬레이션 + **모든 게임 데이터의 편집기**. 밸런스 탭 맨 위의 "지금 피해 공식"은 지금 값이 들어간 식을 보여 주고, 병종·스킬 탭 맨 위의 **피해 계산기**(`DamageCalculatorPanel`, `lib/damageExplain.ts`)는 장수 둘과 스킬을 골라 지금 Lab 값으로 피해가 단계별로 어떻게 계산되는지 보여 준다 (엔진 `DamageCalculator`를 그대로 호출). 지금 공식에서 쓰지 않는 입력칸은 흐리게 표시된다. 병종, 장수, 기본 편성, 스킬, 밸런스 수치를 고치고 "파일에 저장"하면 `packages/game-data/data/*.json`이 바뀐다 (저장 내용은 `changelog.md`에 기록).

- 브라우저 종단 간 검증 스크립트 두 개 (게임 화면, Lab)

## 2. 시작하기

환경: Node 22, npm 10 (워크스페이스). TypeScript 7.x, Vite 8, Vitest 5, PixiJS 8, React 19를 쓴다 (일반적인 버전보다 새 것이니 이상하면 먼저 의심한다). Windows + Git Bash에서 작업했다 (`CLAUDE.md`의 함정 참고).

```bash
npm install
npm test                 # 369개 (엔진, 데이터, Lab, 게임 로직/패널). 서버 불필요
npm run typecheck        # 모든 패키지를 각각 tsc -p 로 검사

npm run lab              # Balance Lab http://localhost:5173 (데이터 편집과 "파일에 저장"은 이 개발 서버에서만 된다)
npm run game             # 게임 화면 http://localhost:5174  (설정 → 관전 / 수동 플레이)
npm run e2e:lab          # Lab 브라우저 확인 38개 (먼저 npm run lab). 데이터 파일을 실제로 바꿨다가 끝나면 원래대로 되돌린다
npm run e2e              # 게임 화면 브라우저 확인 37개 (먼저 npm run game, Edge/Chrome 필요)
npm run sim -- --iterations 10000 --lineups random     # CLI 시뮬레이션, 옵션은 README 참고
npm run lab:build / game:build
```

## 3. 구조와 의존 방향

```text
apps/game/           React + PixiJS 전투 화면
apps/balance-lab/    React + Vite. 밸런스 도구 겸 데이터 편집기. 시뮬레이션은 Web Worker, 고친 값은 "파일에 저장" (개발 서버의 /api/data)
packages/battle-engine/   순수 TypeScript. React/PixiJS/DOM에 의존하지 않는다 (tsconfig에서 DOM 타입도 막아 둠)
packages/game-data/       게임 데이터: data/*.json (skills, traits, unitTypes, characters, presets, balance) + changelog.md + 로더
tools/sim/                시뮬레이션 CLI
tools/e2e/                게임 화면과 Lab의 종단 간 검증 스크립트 (DevTools Protocol)
docs/                     HANDOFF.md, design/(설계 문서), spec/(원본 기획서), art/(아트 원본, 프롬프트, 연결 문서)
```

- 엔진은 **데이터를 인자로만 받는다** (`GameData`, `BalanceConfig`). 그래서 게임, Lab, CLI가 같은 엔진을 쓴다.
- 규칙은 화면에서 계산하지 않는다. 화면은 엔진의 `BattleEvent` 스트림을 재생한다.
- 데미지 공식은 `damage.ts`의 `DamageCalculator` 한 곳, 판정은 `judgement.ts` 한 곳이다. 숫자는 코드에 넣지 않고 데이터로 둔다.
- 엔진은 결정적이다. 난수는 시드 기반(`rng.ts`)만 쓰고 `Math.random`은 쓰지 않는다.

엔진 주요 파일: `engine.ts`(라운드 진행, 행동, 반격, 사기, 열 이동, 단계별 API), `damage.ts`(공식), `stats.ts`(스탯 곡선, AP, 병력 보정), `targeting.ts`(사거리), `policy.ts`(커맨드 선택 AI), `simulator.ts`(통계, 무작위 편성), `lineup.ts`, `judgement.ts`.

### 엔진의 단계별 API (수동 플레이의 기반)

```ts
for (let actor = engine.nextActor(); actor; actor = engine.nextActor()) {
  engine.perform(actor, actor.side === me ? 플레이어가_고른_커맨드 : engine.decide(actor));
}
const result = engine.result();
```

`getLegalCommands(actor)`로 선택지와 대상을, `preview(actor, skillId, targetUid)`로 실제 적용될 피해/반격/회복/가드 확률/결계 여부를 미리 본다. `run()`은 이 API 위에서 AI만으로 끝까지 도는 것이고, 단계별로 진행해도 결과(이벤트 포함)가 같다 (테스트로 보장).

### 데이터와 Lab의 흐름

```text
packages/game-data/data/*.json  ←(파일에 저장)←  Balance Lab 작업 중인 값(초안, 브라우저 localStorage)
        │                                              ↑ 데이터 파일이 바뀌면 초안을 버리고 파일 값으로 시작
        └→ 게임 화면, 시뮬레이터(CLI), Lab의 시작값
```

- Lab 저장 줄(모든 탭 위): 파일과 다른 점을 보여 주고 **파일에 저장**, **파일 값으로 되돌리기**, **변경 메모** 칸이 있다. 저장하면 바뀐 값이 `changelog.md`에 `경로: 이전 값 → 새 값`으로 덧붙는다.
- 저장 전 검사(`lib/dataIssues.ts`): 오류가 하나라도 있으면 저장하지 않는다. 장수 삭제 보호(편성에서 쓰는 장수, 장수가 쓰는 병종)와 `shu`/`wei` 편성 필수도 여기서 막는다.
- 데이터 JSON은 Lab이 저장하는 정규 형식이어야 한다 (`fileSync.test.ts`가 확인). 손으로 고치지 않는다.

### 게임 화면의 구조 (`apps/game/src`)

| 계층 | 파일 | 역할 |
|---|---|---|
| 순수 로직 | `battle/viewState.ts` | 이벤트만으로 화면 상태를 재구성하는 리듀서. 엔진 최종 상태와 같음을 테스트로 보장 |
| | `battle/session.ts` | 엔진을 "플레이어 차례까지 AI가 대신 진행"으로 감싼다. 관전은 `playerSide: null` |
| | `battle/controller.ts` | 세션과 화면을 이어 준다. 화면은 `SceneLike` 인터페이스로만 안다 (테스트에서 가짜로 교체) |
| 렌더링 | `render/BattleScene.ts`, `UnitSprite.ts`, `ArmySprite.ts`, `battleArt.ts`, `theme.ts`, `tween.ts` | PixiJS. 이벤트별 연출, 카드, 전장 군단 그림, 좌표 |
| UI | `components/*`, `App.tsx` | 설정, 커맨드 패널, 로그, 화면 호스트 |

아트 연결 방식은 `docs/art/battle-integration.md`: 상단에 평지 전장과 군단(장수 1명 + 병사 3명), 하단에 카드. 그림이 없는 병종은 표식으로 대체한다. 실행용 이미지는 `apps/game/public/art/battle/`에 있다 (한 장이 1.7~2.8MB, 늘리기 전에 해상도/아틀라스 정책을 정한다). 슬롯 좌표는 `render/theme.ts`의 `slotPosition` 한 곳이다.

중앙 지휘 UI는 `BattleView.tsx`의 `.command-dock`으로 카드 사이에 배치한다. 화면 폭 1100px 이하에서는 전장 아래로 내려간다. 커맨드의 규칙/미리보기는 기존 컨트롤러를 그대로 사용하고 로그는 하단에 둔다. 카드 좌표를 바꾸면 `styles.css`의 패널 위치와 e2e의 겹침 검사도 함께 확인한다.

원거리 효과는 `render/rangedEffects.ts`에 있다. `BattleScene`이 직전 `action`의 스킬 ID로 화살/문양/연무를 고르고, `damage`의 실제 대상으로 재생한다. 가드에 의한 대상 변경을 따르며 반격은 근접 연출을 유지한다. 피해 0이면 붉은 피격 점멸을 생략한다. 효과만 추가했으며 엔진/게임 데이터는 변경하지 않는다. 책사·도사의 절제된 문양·기운 방향은 사용자 확정, 색과 형태는 1차 구현 해석이다.

관우·공용 기병은 116px 임시 기준으로 런타임 매핑되어 있다. 출전한 군단에 필요한 텍스처만 로드한다. 원본과 108/116/124px 비교 페이지는 `docs/art/cavalry/`에 있다. 최종 외형/기마 크기는 미확정이며 스탠딩/얼굴 카드는 보류한다. 실제 6대6 양쪽 진영의 기병 로딩 검사 2개를 추가했다. `ART_REVIEW_PATH=docs/art/cavalry/preview.html`을 지정하면 검토 페이지 검사 5개가 추가된다.

2026-10-08 아트 제작 합의: `docs/art/WORKFLOW.md`. 새 이미지 생성보다 기존 에셋 재사용과 코드 배치 검토를 우선한다. 미제작 병종은 표식을 유지하고, 실제 표시 크기에서 필요한 부분만 점진적으로 마감한다. 추가 스탠딩은 대화 화면이 필요할 때 제작한다.

방패병 임시 표식은 방패 모양이며 전장에 가드 확률/해제 상태를 표시한다. `BattleScene.armyLabels`는 모든 군단 그림 위에 놓인 비상호작용 계층이다. `ArmySprite.annotation`을 추가/정리하고 열 이동 시 좌표를 동기화한다. 이름표는 공격 전진 중 원래 위치를 유지한다. 가드/격파/이동/재시작 표시 검증 1개를 e2e에 추가했다.

## 4. 핵심 설계 결정 (값은 데이터 파일과 설계 문서를 본다)

| 항목 | 결정 |
|---|---|
| 전투 방식 | **라운드제 + AP 총량.** 라운드마다 속도순으로 AP가 남은 군단이 1회 행동. AP는 전투 전체 예산이고 회복되지 않는다. 대기는 AP를 쓰지 않는다. **총 AP = 병종 기본 AP + 장수 행동력으로 얻는 추가 AP** (행동력 2마다 1, 상한 10) |
| HP | 군단전은 **병력**. 군단 레벨당 +50 (Lv1 300, Lv15 1000). 병종 병력 배율을 곱한다 (위 요약). 환산 병력이 켜져 있어 병력 배율은 피해 세기에 영향을 주지 않는다 (끄면 원작처럼 실제 병력 수로 계산). 징병 단가(`recruit`)는 데이터만 있다 |
| 사거리와 열 | 거리(전↔전 1, 후↔전 2, 후↔후 3)가 사거리 이하여야 공격한다. 보병/방패병은 사거리 1(전열에서 적 전열만), 기병은 2(전열에서 적 후열까지, 후열에 서면 적 전열만), 궁병/책사/도사/풍수사는 3(모든 열). 방/보/기/궁은 전열과 후열 모두 배치 가능, 지력 계열은 후열 전용. 무작위 편성은 사거리 1은 전열, 3은 후열, 2는 공격할 수 있는 열 중 무작위. 전열이 비면 후열이 전열이 된다 |
| 반격 | 근접 일반공격만 받는다. 반격 비율은 **공격 기술의 값**(`skill.counterRate`, 지금 0.25)이고 반격자가 계수 1로 친 피해에 곱한다. **맞기 전 병력**으로 계산한다 (원작 방식). 지금은 보병/방패병만 반격한다 (`canCounter`). 원거리(화살/책략)는 일방적 |
| 상성 | **상성표 없음, 병종 특성도 지금은 쓰지 않는다.** 병종 차이는 병종 값(스탯 보정, 받는 피해 배수, 대상 열에 따른 주는 피해 배수, 가드, 반격)으로 표현한다. 특성 체계(`traits.json`)는 엔진에 남아 있고 모든 병종의 `traitIds`는 비어 있다. 화면(UI)에서는 뺐다 |
| 가드 | 방패병이 쓴다. 같은 열 아군을 대신 맞을 확률. 시작 50, 가드 한 번에 지력 × 20, 가드 중에 맞을 때마다 −40 (원작 방식), 가드 중 받는 피해 ×0.5. 공격하면 풀리고 책략은 막지 못한다. 가드 AI: `protect`(같은 열 아군 중 AP가 남은 아군이 있으면 유지, 기본) / `never` |
| 버프 | 책사 "독려": 아군 하나의 공/방/지/속 중 무작위 1~3가지 +1. 도사 "결계": 아군 하나의 다음 피해 1회를 0으로. AP 1, 한 아군에게 1회. AI 성향 `buffMode`: first(기본) / opening / half / never |
| 풍수사 | 기본 공격은 약한 활 공격(`geomancer-shot`, 공격력 기반), 치유(`heal`)는 지력 기반으로 아군만. 장수가 아직 없다 |
| 피해 | **격차식(`gap`, 기본, 2026-10-08 사용자 확정)**: `기본 피해(공격 × 공격 계수 60 × 스킬 계수) × clamp(1 + (공격 − 방어) × 0.1, 하한 0.3) × 대상 열 배수 × 병력 보정(상대 비교) × 가드 배수 × 받는 피해 배수(물리/책략, 지금 모두 1) × 사기 보정(지금 ×1)`, 크리티컬 10% ×1.5. 책략은 지력 − 대상 지력. 방어 무시가 있으면 방어에서 뺀다. 다른 공식도 Lab에서 고를 수 있다: `additive`(원작식, `(병종 보정 + 대상 취약 + 공격×10 − 방어×8, 최소 10) × 10`, 병력 보정은 구간식과 함께 쓰도록 만들었다), `divide`(처음 공식, 공격 × 계수 ÷ (1 + 방어 × 0.1)). 병종 덧셈 보정(`typeBonus`, `vulnerability`)은 `additive`에서만 쓰고, `gap`에서는 `gap.bonusDiv`가 0보다 클 때만 쓴다 (지금 0). **Lab에서 지금 공식이 쓰지 않는 칸을 고쳐도 결과가 바뀌지 않는다** (공격 계수는 원작식에서, 병종 보정·취약은 격차식에서 무시된다) |
| 크리티컬 | 일반공격/책략이 고정 확률(기본 10%)로 피해 ×1.5. 반격과 치유는 제외, 확률 0이면 꺼짐 (`balance.critical`) |
| 사기 | 제로섬 단일 막대, 5:5 시작, **피해에 영향 없음**(코드는 있고 `maxEffect`로 켠다), 최종 판정에서만 사용 |
| 판정/종료 | 전멸 군단 수 → 잔여 병력 → 사기 → 방어측. 종료는 전멸 / 모두 AP 소진 / 교착 / `maxTurns` |
| 장수 | 스탯 8종(공격/방어/지력/속도/행동력/외교/내정/매력, 뒤의 셋은 아직 전투에서 안 쓰임), 병종, 등급(네임드/평범), 레벨. 이름만 삼국지이고 수치는 모두 임시값 |
| 편성과 시나리오 | 기본 편성은 `presets.json`(촉, 위, 황건적, 촉 초반(유관장), 황건적 쉬움/보통/어려움). 무작위 편성은 기본으로 네임드만 쓰고(`pool`), 사거리 3은 후열, 사거리 1은 전열에 둔다 |
| 대상 선택 AI | 기본 "예상 피해가 큰 적". 시뮬레이션과 상대편 AI에 쓰는 가정이며 결과를 크게 좌우한다. 책략이 가드에 막히지 않는데 AI는 가드 감소만 본다는 한계가 있다 |

문서의 확정도 표기: **[확정]**(사용자가 직접 결정) · **[기본값]**(제안했고 이의 없이 채택) · **[임시]**(수치 가설) · **[미정]**. 이 표기를 유지한다.

## 6. 검증 방법과 주의점

- **단위/통합 테스트**(`npm test`)로 로직을 보장한다. PixiJS 캔버스는 Node에서 테스트할 수 없어서, 컨트롤러가 화면을 `SceneLike`로만 알도록 분리해 로직은 가짜 화면으로 테스트한다.
- **데이터 테스트는 값을 고정하지 않는다.** 병종, 스킬, 밸런스 수치는 Lab에서 계속 바뀌므로 구조 규칙(가드 설정과 스킬의 짝, 사거리, 파일 정규 형식 등)만 확인한다. 값에 의존하는 시험은 현재 값에서 출발하게 쓴다 (사용자가 저장한 값 때문에 시험이 깨진 적이 있다).
- **캔버스와 클릭은 `npm run e2e`(37개)로 확인한다.** 설치된 Edge/Chrome을 헤드리스로 띄워 DevTools Protocol로 조작한다. Playwright는 쓰지 않는다. 스크린샷은 `out/e2e/`에 저장된다. 중앙 지휘 패널의 카드 겹침과 390px 화면의 배치, 원거리 효과의 좌우 발사/가드/반격/결계/즉시 재생/화면 종료도 검사한다. 효과 검증은 저장된 데이터를 바꾸지 않는 렌더러용 이벤트로 수행한다.
- **Lab은 `npm run e2e:lab`(38개)으로 확인한다:** 모든 탭, 편집, "파일에 저장"이 `data/*.json`과 `changelog.md`를 실제로 바꾸는 것, 오류가 저장을 막는 것, 파일이 바뀌면 초안이 갱신되는 것. 이 스크립트는 데이터 파일을 건드리므로 끝나면(실패해도) 원래 내용으로 되돌린다. 저장 API가 있는 개발 서버가 필요하고, 이미 켜 둔 서버가 옛 설정이면 껐다 켜거나 `LAB_URL`로 다른 포트를 쓴다.
- Lab 저장 형식(상태의 모양)이 바뀌면 저장 키 버전(`samgukji-balance-lab-v27`)을 올린다. 새 필드를 추가하면 `LabContext.tsx`의 `normalizeState`에서 빠진 값만 채운다 (**기존 값의 순서를 바꾸지 않는다.** 순서가 바뀌면 저장하지 않았는데 "저장 안 됨"이 뜬다).
- 병종/캐릭터별 승률은 **무작위 편성** 모드에서만 의미가 있다 (고정 편성은 편성 편향이 섞인다).
- 개발 서버는 사용자가 이미 켜 두었을 수 있다. 끄지 말고 다른 포트로 확인용 서버를 따로 띄운다. `vite.config.ts`를 바꾸면 켜져 있는 서버는 옛 설정이다 (**Lab 개발 서버를 재시작해야** 저장 API와 변경 기록이 동작한다).
- 새 이벤트 종류를 엔진에 추가하면 `viewState.ts`, `eventText.ts`, `BattleScene.ts`, Lab의 `battleLog.ts`에 모두 반영한다. `npm run typecheck`를 먼저 돌리면 누락이 보인다.
- 가드 이벤트 순서: 행동 → `intercept` → `guardChange` → `damage`.
- **저장소 안에 `git worktree`를 만들지 않는다.** 지우는 순간 `apps/balance-lab`이 비워진 적이 있다 (`git checkout -- apps/balance-lab`으로 복구).

## 7. 시뮬레이션에서 알게 된 것 (함정)

- **AI 정책이 결과를 크게 좌우한다.** 타겟/가드/버프 AI만 바꿔도 병종 승률이 크게 변한다. 비교할 때는 AI 설정을 고정하거나 범위로 본다.
- **데이터 파일은 사용자가 Lab에서 저장하면 바뀐다.** 시뮬레이션 숫자가 예전과 다르면 먼저 `changelog.md`와 `git diff -- packages/game-data/data`를 본다 (엔진 변경이라고 착각해 헤맨 적이 있다).
- 현재 값(무작위 편성 1만 회, 시드 3, 격차식 + 상대 비교 + 크리티컬, 2026-10-08 확정값)의 대략: 방패병 승률 56%/생존 52%, 기병 56%/생존 39%, 궁병 52%, 보병 48%, 도사 45%, 책사 37%. 평균 약 4.3라운드, 공격측 승률 50%. 자세한 표는 `README.md`. 책사/도사가 약하지만 **지금은 그대로 둔다** (방침).
- 책사/도사는 기본 AI(버프 우선)에서 공격을 거의 안 한다 (준 피해 48, 17). 버프 AI를 `never`로 하면 책사 52%(준 피해 956), 도사 52%(1079)가 되고 전멸 종료가 74%로 는다. 1대1로 재면 책사는 늘 불리하다 (기병이 속도로 먼저 치고, 병력 비례 피해라 맞은 책사는 약해진다).
- 대상 선택 AI는 책략이 가드에 막히지 않는다는 규칙을 모른다. 그래서 가드 중인 방패병을 낮게 평가하고 지력이 낮은 궁병을 먼저 노릴 수 있다 (책사/도사가 전열만 노려도 승률은 거의 같았다).
- **지금 값에서는 전투의 절반 이상이 전멸로 끝난다** (전멸 57%, AP 소진 32%, 교착 11%). 처음 공식(절대 병력 보정)은 전멸이 0.3%였다. 전멸을 늘린 것은 상대 비교 병력 보정(병력이 줄면 피해도 비율로 줄지만, 큰 쪽은 최대 1.5배까지 세진다)과 크리티컬, 공격 계수 60이다.
- **병력 배율과 가드 피해 배수는 병력 보정 방식에 따라 결과가 크게 다르다.** 원작식 + 구간식 + 실제 병력 수에서는 방패병 1.5배 + 가드 ×0.5면 생존 99.9%(거의 안 죽음)였지만, 지금(환산 병력 켜짐, 상대 비교)은 같은 값으로 생존 52%다. 환산 병력이 켜져 있으면 병력 배율은 HP만 늘리고 피해 세기는 늘리지 않는다.
- 병력 보정 `relative`(지금 기본)는 큰 군단이 작은 군단을 칠수록 세진다. 맞아서 병력이 줄면 약해지는 눈덩이 효과가 절대 방식보다 크다.
- 후열에 방패병을 두고 가드 AI `protect`면 후열의 책사/도사가 거의 안 맞지만 전투가 대부분 교착으로 끝난다.
- 풍수사를 넣은 편성은 치유 계수 때문에 승률이 크게 오른다 (임시 장수로 시험). 치유량은 아직 정하지 않았다.
- 전열 전멸 시 후열 이동 규칙은 기본 수치에서 거의 발동하지 않는다. 시작할 때 전열이 비어 있는 편성에서는 발동한다.
- 사기를 피해 보정으로 쓰면 짧은 전투에서 증폭되어 방어측이 73% 이겼다. 그래서 피해 영향을 껐다.
- 한 판에 약 40번 행동하고, 1배속에서 약 1분이 걸린다 (화면의 기본 속도는 2배).
- 통계의 `damageTaken`은 병력에서 막히므로 "더 센 공격"의 지표로 못 쓴다. 생존율, 라운드 수, 평균 준 피해를 본다.
- 이벤트 `battleEnd`는 `engine.result()`를 처음 부를 때 만들어진다. `PlaySession.advance()`가 종료 시점에 `result()`를 불러서 화면이 재생할 수 있게 한다.

## 8. 확장 계획이 코드에 주는 영향

사용자는 나중에 **9대9**와 **공성 상황**으로 넓힐 계획이다. 지금은 6대6 기준이다.

| 위치 | 현재 | 확장 시 |
|---|---|---|
| `lineup.ts` | `MAX_UNITS_PER_SIDE = 6`, `ROW_CAPACITY = 3` | 9로 올리고 열 구조를 정한다 |
| `types.ts` `Row` | `'front' \| 'back'` 2열 | 3열(전/중/후)이면 `Row`, 거리 계산, `allowedRows`, `damageDealtByRow`, 특성의 `versus.rows`, 전열 이동, 설계 문서가 모두 바뀐다 |
| Lab `slots.ts` 등 | `SLOT_COUNT = 6`, `FRONT_SLOTS = 3`, `teamA.length === 6` 검증, `LineupEditor`, 기본 편성 편집 | 슬롯 수와 열 표시를 일반화한다 |
| 게임 화면 `render/theme.ts`, `UnitSprite.ts`, `ArmySprite.ts`, `BattleScene.ts` | 열 2개 × 행 3개 좌표, 카드 고정 크기, 군단 배치 | 카드 크기와 배치를 다시 설계한다 |
| 판정/사기 | 군단 수 가변은 이미 지원 | 그대로 쓸 수 있다 |
| 공성 | 없음 | 날씨·지형·성벽 같은 전장 요소는 새 규칙이므로 `docs/design/`에 먼저 정의한다 |

어려운 것은 **열이 2개를 넘을 때의 규칙**과 그에 맞는 **화면 배치**다.

## 10. 작업 방식 (사용자 선호와 합의)

> 개발 규칙은 `CLAUDE.md`(에이전트 공통 안내는 `AGENTS.md`)에 모여 있다. 아래는 합의의 배경이다.

- 사용자는 한국어로 소통하고, 웹 프론트엔드(React) 경험이 있다. 게임 엔진(Unity)은 쓰지 않기로 했다.
- **기획을 확정하고 문서화한 뒤 구현한다.** 해석이 들어간 부분은 "제 해석"이라고 밝히고 문서에 [기본값]/[미정]으로 남긴다.
- **게임 디자인은 사용자가 정한다.** 규칙, 수치, 병종 개성을 임의로 정하지 않는다. 정하지 않은 선택은 가장 단순한 해석으로 하되 밝히고, 구조가 바뀌면 먼저 묻는다.
- **병종 간 수치를 정밀하게 맞추자고 먼저 제안하지 않는다.** 값이 깨졌을 때만 보고한다.
- **난이도는 적 스탯 ±1로 조절한다** (사용자 합의). 계수는 전투 전체의 속도를 맞추는 값으로 쓴다. 격차식 기준으로 계수 ±5는 남은 병력 2~3%밖에 안 움직이지만 적 스탯 ±1은 손실을 두 배 가까이 바꾼다. 지금 값에서 초반 시나리오(유관장 대 황건적, 2천 회)는 쉬움/보통/어려움 모두 유관장이 이기고, 남은 병력은 2825 / 3036 / 2526이다.
- **피해 공식은 사용자가 Lab에서 직접 비교해 정한다.** 2026-10-07~08에 처음 공식 → 원작식 → 격차식 → 원작식 → 격차식으로 여러 번 바꿔 보았고, 격차식 + 상대 비교 + 받는 피해 배수 1로 확정했다. 공식과 병력 보정 방식을 바꾸면 같은 병종 값의 의미가 달라지므로, 수치를 고칠 때는 지금 어느 공식인지 먼저 본다.
- 숫자는 데이터로 분리하고, 전투 로직과 렌더링을 분리한다. 임시 UI와 임시 아트를 쓴다.
- **원작(전국란스)은 참고만 한다.** 처음에는 게임 파일을 열지 않기로 했지만, 플레이로 관찰하는 데 시간이 너무 걸려서 사용자가 범위를 넓혔다 (2026-10-07): 게임 스크립트에서 병종 간 수치와 전투 공식만 읽는다. 정리한 것은 `docs/reference/sengoku-rance-battle.md`이고 플레이 실측과 대조했다. 기본 틀은 우리 것을 쓰고, 원작 값을 데이터 파일에 그대로 옮기지 않는다. 그림, 대사, 코드는 가져오지 않는다.
- 실험할 때는 `tools/sim/` 아래에 임시 스크립트를 만들어 `npx tsx`로 돌리고 **삭제한다.** 오래 쓸 도구는 CLI 옵션, Lab 기능, `tools/e2e`로 승격한다.
- 결과를 보고할 때는 측정값과 추정을 구분하고, 확인하지 못한 것은 확인하지 못했다고 쓴다. 비교는 같은 시드와 같은 AI 설정으로 한다.
- 커밋과 푸시는 사용자가 요청했을 때만 한다.
