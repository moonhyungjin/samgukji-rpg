# 인계 문서

이 프로젝트를 이어받는 사람(또는 에이전트)을 위한 문서다. 먼저 이 문서를 읽고, 규칙은 `docs/design/`, 원본 기획서는 `docs/spec/`, 수치 관찰은 루트 `README.md`를 본다.

## 1. 한 줄 요약

삼국지 소재의 6인 그리드 전략 RPG(전국란스 스타일)에서 **전투 엔진 + Balance Lab + 전투 화면**을 만들어 전투의 재미와 밸런스를 검증하는 단계다.
정식 게임이 아니라 "숫자를 바꿔 가며 계속 싸워보고 싶은 전투 샌드박스"가 첫 성공 기준이다.

- 완료: 순수 TypeScript 전투 엔진, 시뮬레이터, CLI, Balance Lab, **PixiJS 전투 화면(관전 + 수동 플레이)**, 브라우저 종단 간 검증 스크립트
- 다음: 직접 플레이해 보고 규칙/수치 결정 → 규칙 확장(가드, 필살기, 상태이상, 승급)
- 지금은 지역 제패, 스토리, 아트, 캐릭터 대량 제작을 하지 않는다.

## 2. 시작하기

환경: Node 22, npm 10 (워크스페이스). TypeScript 7.x, Vite 8, Vitest 5, PixiJS 8, React 19를 쓴다 (일반적인 버전보다 새 것이니 이상하면 먼저 의심한다).

```bash
npm install
npm test                 # 302개 (엔진, 통합, Lab, 게임 로직/패널)
npm run typecheck        # 5개 패키지를 각각 tsc -p 로 검사

npm run game             # 게임 화면 http://localhost:5174  (설정 → 관전 / 수동 플레이)
npm run lab              # Balance Lab (터미널에 나오는 주소)
npm run e2e:lab          # Lab 브라우저 확인 35개 (먼저 npm run lab. 장수/병종/기본 편성 편집, 파일에 저장, 검사, 파일 변경 감지. 끝나면 데이터 파일을 원래대로 되돌린다)
npm run e2e              # 게임 화면을 실제 브라우저로 조작해 확인 23개 (먼저 npm run game, Edge/Chrome 필요)
npm run sim -- --iterations 10000 --lineups random     # CLI 시뮬레이션, 옵션은 README 참고
```

## 3. 구조와 의존 방향

```text
apps/game/           React + PixiJS 전투 화면
apps/balance-lab/    React + Vite. 밸런스 도구 겸 데이터 편집기. 시뮬레이션은 Web Worker에서 실행, 고친 값은 "파일에 저장" (개발 서버의 /api/data)
packages/battle-engine/   순수 TypeScript. React/PixiJS/DOM에 의존하지 않는다 (tsconfig에서 DOM 타입도 막아 둠)
packages/game-data/       게임 데이터: data/*.json (skills, traits, unitTypes, characters, presets, balance) + 로더. 엔진의 "타입"만 가져온다
tools/sim/                시뮬레이션 CLI
tools/e2e/                게임 화면 종단 간 검증 스크립트 (DevTools Protocol)
docs/                     HANDOFF.md, design/(설계 문서 01, 02), spec/(원본 기획서 v0.1)
```

- 엔진은 **데이터를 인자로만 받는다** (`GameData`, `BalanceConfig`). 그래서 게임과 Lab이 같은 엔진을 쓴다.
- 규칙은 화면에서 계산하지 않는다. 화면은 엔진의 `BattleEvent` 스트림을 재생하는 쪽이다.
- 데미지 공식은 `DamageCalculator` 한 곳, 판정은 `judgement.ts` 한 곳이다. 숫자는 코드에 넣지 않고 `game-data`의 데이터로 둔다.
- 엔진은 결정적이다. 난수는 시드 기반(`rng.ts`)만 쓰고 `Math.random`은 쓰지 않는다. 1대1처럼 속도가 다르면 결과도 매번 같다.

엔진 주요 파일: `engine.ts`(라운드 진행, 행동, 반격, 사기, 열 이동, 단계별 API), `damage.ts`, `targeting.ts`, `policy.ts`(커맨드 선택 AI), `simulator.ts`(통계, 무작위 편성), `lineup.ts`, `judgement.ts`.

### 엔진의 단계별 API (수동 플레이의 기반)

```ts
for (let actor = engine.nextActor(); actor; actor = engine.nextActor()) {
  engine.perform(actor, actor.side === me ? 플레이어가_고른_커맨드 : engine.decide(actor));
}
const result = engine.result();
```

`getLegalCommands(actor)`로 선택지와 대상을, `preview(actor, skillId, targetUid)`로 실제 적용될 피해/반격/회복을 미리 본다. `run()`은 이 API 위에서 AI만으로 끝까지 도는 것이고, 단계별로 진행해도 결과(이벤트 포함)가 완전히 같다 (테스트로 보장).

### 게임 화면의 구조 (`apps/game/src`)

| 계층 | 파일 | 역할 |
|---|---|---|
| 순수 로직 | `battle/viewState.ts` | 이벤트만으로 화면 상태를 재구성하는 리듀서. 엔진 최종 상태와 같음을 테스트로 보장 |
| | `battle/session.ts` | 엔진을 "플레이어 차례까지 AI가 대신 진행"으로 감싼다. 관전은 `playerSide: null` |
| | `battle/controller.ts` | 세션과 화면을 이어 준다. 이벤트를 하나씩 재생하며 로그/선택지를 만든다. 화면은 `SceneLike` 인터페이스로만 안다 (테스트에서 가짜로 교체) |
| 렌더링 | `render/BattleScene.ts`, `UnitSprite.ts`, `theme.ts`, `tween.ts` | PixiJS. 이벤트별 연출, 카드, 좌표 |
| UI | `components/*`, `App.tsx` | 설정, 커맨드 패널, 로그, 화면 호스트 |

화면의 논리 좌표는 1280×600이고 실제 크기에 맞춰 통째로 확대/축소한다. 슬롯 좌표는 `render/theme.ts`의 `slotPosition` 한 곳이다.

## 4. 핵심 설계 결정 (자세한 내용은 설계 문서)

| 항목 | 결정 |
|---|---|
| 전투 방식 | **라운드제 + AP 총량.** 라운드마다 속도순으로 AP가 남은 군단이 1회 행동. AP는 전투 전체 예산이고 회복되지 않는다 (풍수사 AP 회복형 승급만 예외, 미구현). 행동 게이지는 폐기 |
| HP | 군단전은 **병력**. 군단 레벨당 +50 (Lv1 300, Lv15 1000) |
| 피해 | 병력이 많을수록 강하다 (`clamp(현재 병력 / 1000, 0.3, 1.75)`). 방어는 `1 / (1 + 방어 × 0.1)`, 책략은 대상의 지력으로 경감 |
| 반격 | 근접 일반공격만 반격 피해를 받는다 (× 0.5). 원거리(화살/책략/독연)는 일방적 |
| 상성 | **상성표 없음.** 병종 차이는 "특성"(조건부 피해 보정)으로 표현하는 체계가 있으나, 지금은 어떤 병종에도 붙이지 않았다 |
| 사기 | 제로섬 단일 막대, **5:5 시작, 피해에 영향 없음, 최종 판정에서만 사용**. 판정에서의 구체적 쓰임은 해석이 들어 있다 (아래 미정) |
| 판정 | 전멸 군단 수 → 잔여 병력 → 사기 → 방어측 |
| 종료 | 한쪽 전멸 / 모두 AP 소진 / 교착(한 라운드 동안 대기 외 행동 없음) / `maxTurns` 40 |
| 열 | 전열 3 + 후열 3. 전열이 전멸하면 후열이 즉시 전열이 된다 |
| 가드 | **방패병(`shield`, 장비·허저)이 처음부터 쓴다. 보병(`infantry`, 위연·전위)은 쓰지 않는다. 가드 상태(확률>0)인 동안 받는 피해 ×0.75 (25%만 줄임).** 궁병이 전열을 때리면 피해 ×0.8, 후열이면 ×1(특성 `archer-vs-front`). 궁병 병력 배율 0.85, 궁병 생존율 목표 40%. 같은 열 아군을 대신 맞을 확률 (시작 50%p, 가드 커맨드 +70, 막을 때 −40, 공격하면 해제). 책략/독연은 막지 못함. AI는 지킬 같은 열 아군(**AP가 남아 아직 싸울 수 있는 아군**)이 있으면 가드를 100%까지 올려 유지하고 공격하지 않음 (`protect`). 아군이 모두 AP를 다 썼으면 지킬 필요가 없어 공격한다 |
| 버프 AI 성향 | `buffMode`: first(기본, 대상이 남아 있으면 먼저) / opening(1라운드만) / half(절반 확률) / never(공격만). Lab 시뮬레이션 설정과 CLI `--buff-policy`. 사람은 섞어서 쓰므로 범위로 본다 |
| 버프 | 책사 "독려"는 아군 하나의 **공/방/지/속 중 무작위 1~3가지를 +1** (전투 끝까지, 한 아군에게 1회), 도사 "결계"는 아군 하나의 **다음 피해 1회를 0으로 무시** (전국란스의 음양사 느낌). 둘 다 AP 1, 병력과 무관하게 아군을 돕는다. AI는 쓸 대상이 남아 있으면 공격보다 먼저 쓴다: 스탯 버프는 주력 공격 스탯(공격 또는 지력)이 가장 높은 아군에게, 결계는 전열(방어가 낮은 순)부터. 횟수와 폭은 Lab에서 조정 |
| 병력 배율 | 풍수사 0.6, 책사 0.8, 도사 0.8, 기병 0.8, 궁병 0.85 (병력이 비싼 병종), 나머지 1. 치유량은 줄지 않는다 |
| 받는 피해 배수 | 물리(일반공격/돌격/화살)와 책략(책략/독연)을 구분한다. 방패병/보병/기병/궁병은 물리 ×1, 책략 ×1.1, 책사/도사/풍수사는 물리 ×1.1, 책략 ×0.8. 물리 공격수(특히 궁병)가 지력 계열을 잡는 전문가가 되고, 지력 계열끼리는 서로 덜 아프다 |
| 병종별 반격 비율 | 방패병 0.5, 보병 0.5, 기병 0.6, 궁병 0.25. 기병의 반격에는 방어 무시가 붙지 않는다. 생략하면 `balance.counter.rate`(0.5). 나중에 방패병 승급에서 반격을 더 세게 하는 방향 |
| 평범한 장수 | `rank: 'normal'` 캐릭터 12명(병종마다 2명, 스탯이 네임드의 절반 안팎)과 기본 편성 `yellow`. 무작위 편성은 기본으로 네임드 장수만 쓰고 `--pool normal|all`(Lab: "무작위 편성 후보")로 바꾼다 |
| 초반 시나리오 | 촉은 유관장(유비 보병, 관우 기병, 장비 방패병, 편성 `shuStart`)으로 시작해 황건적과 싸운다. 황건적은 쉬움 `yellowEasy`(보,보,방), 보통 `yellowNormal`(보,방,궁), 어려움 `yellowHard`(보,보,방 + 궁 후열)로 나눈다. `npm run sim -- --team-a shuStart --team-b yellowHard`. Lab 편성 탭에도 버튼이 있다. 유비는 새 캐릭터(보병, 공7 방6 지6 속5 행동력3 매력10, 임시값) |
| 병종 스탯 보정 | 방패병 공−1 속−1 (방어 보정은 제거), 기병 공/방/속 +1, 궁병 방−1 속−1, 책사 지+1, 도사 속+1 (`statMods`, 캐릭터 기본 스탯에 더함). 승급하면 보정 추가 예정 |
| AP | **AP = 병종 기본 AP + 캐릭터 행동력 추가 AP.** 병종 기본 AP: 방패병 3, 보병/기병/궁병 2, 책사/도사/풍수사 2. 행동력 스탯(1~10)은 2마다 추가 AP 1 (올림, `balance.action`으로 조정). 예: 행동력 3이면 +2. 캐릭터마다 다르게 둔다. 초반엔 행동력 대체로 5 이하(+3), 10(+5)까지는 아이템 등으로 올리는 방향. 지금 캐릭터 행동력은 방패병/보병/기병/궁병 3, 책사/도사 1이라 총 AP는 방패병 5, 보병/기병/궁병 4, 책사/도사 3 |
| 기병 | **돌격 계수 1.2, 방어 1 무시(`ignoreDefense`), 받는 피해 ×0.9(`cavalry-tough`).** **사거리 1**이라 전열에서 적의 전열만 칠 수 있다. 후열 저격은 승급 병종에서 다시 정한다 |
| 사거리 | 공격자와 대상의 거리(전열↔전열 1, 후열↔전열 또는 전열↔후열 2, 후열↔후열 3)가 사거리 이하여야 공격할 수 있다. 방패병/보병/기병은 사거리 1 — 자기가 전열일 때 적의 전열만 칠 수 있고, 후열에 서면 아무도 못 친다. 궁병/책사/도사/풍수사는 사거리 3 — 어느 열에서든 모든 열을 칠 수 있다. 방/보/기/궁은 시작할 때 전열과 후열 어디에든 배치할 수 있고, 책사/도사/풍수사는 후열 전용이다. 전열이 전멸하면 후열이 전열이 된다 (시작할 때 전열이 비어 있어도 마찬가지) |
| 병종 | 7계열(보병, 방패병, 기병, 궁병, 책사, 도사, 풍수사) × 승급 2갈래. 승급 병종은 미구현. 병종은 캐릭터당 고정 |
| 커맨드 | 일반공격 + 특수행동 + 필살기(유니크) + 대기. 일반공격은 병종이 정의하고 승급하면 2로 교체 |
| 대상 선택 AI | 기본 "예상 피해가 큰 적". 시뮬레이션과 상대편 AI에 쓰는 가정이며 결과를 크게 좌우한다 |

문서의 확정도 표기: **[확정]**(사용자가 직접 결정) · **[기본값]**(제안했고 이의 없이 채택) · **[임시]**(수치 가설) · **[미정]**. 이 표기를 유지한다.

## 5. 구현 현황

| 구현됨 | 아직 없음 |
|---|---|
| 일반공격, 치유, 대기, **가드(방패병)와 대신 맞기, 버프(책사 무작위 스탯 +1 / 도사 피해 1회 무시)**, 반격, 병력 비례 피해, 병종 특성 체계, 제로섬 사기, 전열 전멸 시 후열 이동, 승패 판정, 교착 종료, 진영당 1~6군단 가변 편성, 무작위 편성 모드, 병종별 병력 배율(`troopScale`), 치유 병력 보정 옵션, **엔진 단계별 API, 커맨드 미리보기, PixiJS 전투 화면(관전/수동 플레이/건너뛰기/속도), 브라우저 종단 간 검증** | 필살기, 상태이상(화상/독/젖음), 책략의 날씨·지형 변환, 승급 병종, AP 회복, 아이템, 군단 경험치, 일기토/개별 레벨/토벌, 특수 병종 |

책략/독연은 지금 피해만 준다. 장수 27명(네임드 15명 + 평범한 장수 12명)과 수치는 전부 임시값이고 이름만 삼국지다. **모든 게임 데이터의 원본은 `packages/game-data/data/*.json`** (skills, traits, unitTypes, characters, presets, balance)이고, Balance Lab에서 고치고 "파일에 저장"한다. **풍수사 병종은 있지만 캐릭터가 없다** (곽가를 도사로 바꿨다). 

## 6. 검증 방법과 주의점

- **단위/통합 테스트**(`npm test`)로 로직을 보장한다. PixiJS 캔버스는 Node에서 테스트할 수 없어서, 컨트롤러가 화면을 `SceneLike`로만 알도록 분리해 로직은 가짜 화면으로 테스트한다.
- **캔버스와 클릭은 `npm run e2e`로 확인한다.** 설치된 Edge/Chrome을 헤드리스로 띄워 DevTools Protocol로 조작한다 (23개 확인: 버프 로그, 스킬 선택, 가드 확률 표시, 캔버스 카드 클릭, 목록 버튼, 보병 가드, 대기, AI 위임, 애니메이션, 건너뛰기, 다시 하기, 콘솔 오류). Playwright는 쓰지 않는다. 화면을 바꾸면 이걸 다시 돌린다. 스크린샷은 `out/e2e/`에 저장되니 눈으로도 확인한다.
- 같은 방식으로 Balance Lab을 `npm run e2e:lab`(35개)으로 확인한다: 모든 탭, 계수/스탯 입력, 장수/병종/기본 편성 편집, "파일에 저장"이 `data/*.json`을 실제로 바꾸는 것, 오류가 저장을 막는 것, 파일이 바뀌면 초안이 파일 값으로 갱신되는 것. 이 스크립트는 데이터 파일을 건드리므로 끝나면(실패해도) 원래 내용으로 되돌린다. 저장 API가 있는 개발 서버(`npm run lab`)가 켜져 있어야 한다. 이미 켜 둔 서버가 옛 설정이면 껐다 켜거나 `LAB_URL`로 다른 포트를 쓴다.
- **Lab에서 고친 값은 "파일에 저장"을 눌러야 `packages/game-data/data/*.json`에 반영되고, 그래야 게임과 시뮬레이터가 쓴다.** 저장 전의 초안은 브라우저 localStorage에 있다 (키 `samgukji-balance-lab-v26`). 데이터 파일이 바뀌면(저장했거나 git으로 받았으면) Lab은 초안을 버리고 파일 값으로 시작한다 (`lib/fileSync.ts`의 `syncWithFiles`). 파일 없이 값을 옮기는 방법은 "밸런스만 내보내기"(CLI `--balance`로 검증 가능)와 "전체 상태 내보내기"다.
- 저장 형식(Lab 상태의 모양)이 바뀌면 Lab 저장 키 버전을 올린다. 새 필드를 추가하면 `LabContext.tsx`의 `normalizeState`에서 빠진 값만 채운다 (**기존 값의 순서를 바꾸지 않아야 한다.** 순서가 바뀌면 파일과 달라 보여 저장하지 않았는데 "저장 안 됨"이 뜬다. `fileSync.test.ts`가 이를 확인한다).
- 병종/캐릭터별 승률은 **무작위 편성** 모드에서만 의미가 있다 (고정 편성은 편성 편향이 섞인다).
- 게임 화면은 Lab의 초안이 아니라 저장된 `data/*.json`을 쓴다. 데이터 파일이 바뀌면 게임 개발 서버가 페이지를 새로고침한다.
- 새 이벤트 종류를 엔진에 추가하면 `viewState.ts`(상태), `eventText.ts`(로그), `BattleScene.ts`(연출)와 Lab의 `battleLog.ts`에 모두 반영한다. `viewState`는 TypeScript의 exhaustive 검사가 누락을 잡아 주고, 엔진 최종 상태와 같은지 테스트가 확인한다. (가드 이벤트를 추가했을 때 `viewState`를 빠뜨려 테스트 15개가 한꺼번에 깨진 적이 있다. `npm run typecheck`를 먼저 돌리면 바로 보인다.)
- 가드 이벤트는 순서가 중요하다: 행동 → `intercept`(대신 맞음) → `guardChange`(확률 감소) → `damage`. 엔진 테스트가 순서를 확인한다.

## 7. 시뮬레이션에서 알게 된 것 (함정)

- **AI 정책이 결과를 크게 좌우한다.** 같은 데이터에서 타겟 AI만 바꿔도 병종 승률과 생존율이 크게 변한다. 밸런스 수치를 맞추기 전에 AI 가정을 먼저 정한다.
- 집중 공격 AI("현재 병력이 가장 적은 적")는 `troopScale`이 다른 병종을 항상 먼저 노린다 (병력 배율 1.0 → 0.99에서 풍수사 생존율 89% → 22%). 병력 비율 기준으로 고치는 안이 있다.
- 전투의 98%가 전멸이 아니라 AP 소진 후 판정으로 끝난다. 1대1에서는 AP 4로 서로 못 죽이고, 속도 1 차이가 승패를 가른다 (병력 보정 눈덩이).
- **전열 전멸 시 후열 이동 규칙은 기본 수치에서 거의 발동하지 않는다** (150판 중 0번). 규칙 구현은 검증됐지만, 실제 전투에서는 보이지 않는다.
- 사기를 피해 보정(±10%, 시작 60:40)으로 쓰면 5라운드 안팎의 짧은 전투에서 증폭되어 방어측이 73% 이겼다. 그래서 피해 영향을 껐다.
- **전투 종료 방식은 나중에 손봐야 한다.** 지금은 전멸보다 AP 소진/교착(stall)으로 끝나는 전투가 대부분이다 (무작위 편성의 약 12~20%가 교착, 나머지는 AP 소진). 더 빨리 끝나게 하는 방법(공격 유도, AP 총량, 사기 규칙 등)을 다음에 정한다. (사용자 메모)
- 초반 시나리오 신호(유관장 vs 황건적, 가드 protect, 3000판): 쉬움/보통은 촉 100% 승·잃는 군단 0, 어려움(보,보,방+궁)은 촉 99.7% 승이지만 남은 병력이 촉 1522 vs 적 1444로 거의 대등하다. 가드를 쓰지 않으면(never) 어려움에서 유비가 거의 항상 쓰러진다. 관우는 거의 맞지 않는다(받은 피해 약 90).
- 현재 기본 수치의 신호 (무작위 편성 1만 판, 가드 AI protect): 책사 승률 40%/생존 62%, 보병 46%/46%, 방패병 50%/93%, 기병 52%/86%, 도사 46%/57%, 궁병 64%/98% (목표 20%). 궁병이 가장 강하고 한 번도 죽지 않는다 (전열의 기병이 후열을 못 때리고, 책사/도사는 버프에 AP를 쓴다). 수치는 임시이고 조정 대상이다.
- **병력 배율을 낮추면 그 병종이 AI의 동률 처리 때문에 먼저 맞는다.** 책사(방어 3, 병력 800)와 도사(방어 3, 병력 1000)는 예상 피해가 같아서 병력이 적은 책사만 먼저 노려진다 (생존율 책사 36%, 도사 96%). 이건 병종 수치가 아니라 AI 동률 규칙의 결과다.
- 보병 가드 AI(`protect`)는 지킬 아군이 싸울 수 있는 동안 공격하지 않는다 (1만 판에서 일반공격 1.3만 회, 가드 5.8만 회). 전투당 대신 맞는 횟수가 늘어 기병 생존율을 24% → 70%로 올린다. 이게 의도인지는 플레이해 보고 정한다.
- 가드는 공격하면 풀리고 막을 때마다 줄어서, 실제 화면에서는 "가드 120%"가 곧 80%, 40%로 줄어든다. 가드 AI를 `never`로 두면 보병은 일반 공격수가 된다.
- 한 판에 약 37번 행동하고, 1배속에서 약 1분이 걸린다 (4배속 약 15초). 화면의 기본 속도는 2배다. 연출을 더 줄이려면 `UnitSprite.ts`/`BattleScene.ts`의 시간을 줄인다.
- 통계의 `damageTaken`은 병력에서 막히므로 "더 센 공격"의 지표로 못 쓴다. 생존율이나 라운드 수를 본다.
- 이벤트 `battleEnd`는 `engine.result()`를 처음 부를 때 만들어진다. `PlaySession.advance()`가 종료 시점에 `result()`를 불러서 화면이 재생할 수 있게 한다 (예전에 종료 배너가 안 뜨던 버그의 원인이었다).

## 8. 확장 계획이 코드에 주는 영향

사용자는 나중에 **9대9**와 **공성 상황**으로 넓힐 계획이다. 지금은 6대6 기준으로 만들었고, 아래가 고정돼 있다.

| 위치 | 현재 | 확장 시 |
|---|---|---|
| `lineup.ts` | `MAX_UNITS_PER_SIDE = 6`, `ROW_CAPACITY = 3`, `generateRandomLineup`의 기본 크기 6 | 9로 올리고 열 구조를 정한다 |
| `types.ts` `Row` | `'front' \| 'back'` 2열 | 9대9가 3열(전/중/후)이면 `Row`, `TargetRule`, 특성의 `versus.rows`, `advanceRows`(전열 전멸 시 이동), 설계 문서의 "전열/후열"이 모두 바뀐다 |
| Lab `slots.ts` | `SLOT_COUNT = 6`, `FRONT_SLOTS = 3`, `LabContext`의 `teamA.length === 6` 검증, `LineupEditor` | 슬롯 수와 열 표시를 일반화한다 |
| 게임 화면 `render/theme.ts` | 열 2개 × 행 3개 좌표(`COLUMN_X`, `ROW_Y`), 카드 크기, 논리 좌표 1280×600, `slotPosition`이 슬롯 3칸 초과 시 마지막 칸에 겹침 | 9대9면 카드 크기와 배치를 다시 설계한다 (열 3개 또는 행 5개) |
| 게임 화면 `UnitSprite.ts`, `BattleScene.ts` | 카드 200×112 고정, 배경 열 패널 4개 | 위와 함께 수정 |
| 판정/사기 | 군단 수 가변은 이미 지원 | 그대로 쓸 수 있다 |
| 공성 | 없음 | `BattleContext`(날씨·지형)를 아직 만들지 않았다. 성벽/성문 같은 전장 요소는 새 규칙이므로 `docs/design/`에 먼저 정의한다 |

엔진은 "진영당 군단 수"를 이미 가변으로 다루므로(1~6), 수를 늘리는 것 자체는 쉽다. 어려운 것은 **열이 2개를 넘을 때의 규칙**과 그에 맞는 **화면 배치**다.

## 9. 다음 작업 제안

1. **직접 플레이해 본다** (`npm run game`). 수동 플레이에서 재미와 읽기 쉬움을 판단하고, 미정 규칙(아래)을 결정한다. 특히 한 판 길이(약 1분), 책사만 먼저 죽는 것, 보병 가드의 쓰는 맛(가드 AI가 공격을 전혀 하지 않는 것이 의도인지)을 본다.
2. **규칙 확장:** 가드, 필살기, 상태이상, 승급을 확정되는 순서대로 추가한다. 항목마다 엔진 이벤트, 화면 연출, Lab 수치를 같이 넣는다. 선택지가 늘어야 수동 플레이가 의미를 갖는다.
3. **게임 화면 개선:** Lab에서 내보낸 상태를 불러와 같은 수치로 플레이, 유닛 정보 툴팁, 필살기 연출, 효과음/아트(시스템이 확정된 뒤).

미정 결정 사항은 `docs/design/01-...md` 8장, `02-...md` 8장의 표에 모여 있다. 특히 급한 것:

- 사기를 최종 판정에 쓰는 방식 (지금은 3번째 동률 기준이라 사실상 영향이 없다. `balance.morale.judgement`로 순서를 바꿔 볼 수 있다)
- 필살기 배율, 2단계 군단 일반공격에 반격을 적용할지
- 가드의 광역/책략 처리 외 세부, 도사 승급 방향
- 병종 간 균형을 어떤 AI 가정으로 볼지

## 10. 작업 방식 (사용자 선호와 합의)

- 사용자는 한국어로 소통하고, 웹 프론트엔드(React) 경험이 있다. 게임 엔진(Unity)은 쓰지 않기로 했다.
- **기획을 확정하고 문서화한 뒤 구현한다.** 해석이 들어간 부분은 "제 해석"이라고 밝히고 문서에 [기본값]/[미정]으로 남긴다.
- 숫자는 데이터로 분리하고, 전투 로직과 렌더링을 분리한다. 임시 UI와 임시 아트를 쓴다. 아트를 먼저 만들지 않는다.
- **원작(전국란스) 게임 파일을 추출·디컴파일하지 않기로 했다** (EULA/저작권, Steam 출시 목표, 원작 수치가 우리 규칙과 맞지 않음). 원작은 사용자의 설명과 직접 플레이한 관찰로만 참고한다. 원작 세부 규칙에 대한 설명은 기억 기반이라 틀릴 수 있다.
- 실험할 때는 `tools/sim/src/_이름.ts` 임시 스크립트를 만들어 `npx tsx`로 돌리고 **삭제한다.** 저장소에 남기지 않는다. 오래 쓸 도구는 CLI 옵션, Lab 기능, `tools/e2e`로 승격한다.
- 결과를 보고할 때는 측정값과 추정을 구분하고, 확인하지 못한 것은 확인하지 못했다고 쓴다. (이번에도 테스트가 실제 버그 두 건을 잡았다: 미리보기의 사기 반영 누락, 종료 이벤트 재생 누락.)
